## 1. Jev の基本仕様（実測で確認したこと）

| 項目 | 実測値 |
|---|---|
| エンドポイント | `POST https://jevtypesafeai.com/api/v1/decide` |
| モデル | `jev-latest` は `jev-1.13.0` に解決される |
| 質問タイプ | `noul` / `choice` / `score` すべて実働確認済み |
| 1コールに複数質問 | 可能。異なるタイプの混在も可 |
| レイテンシ | 1問 3〜5秒。並列6で90問15秒 |
| レスポンス | `usage` に `input_tokens` / `output_tokens` / `cost_usd` / `credits_remaining_usd` |

### レスポンス例（noul）

```json
{
  "model": "jev-1.13.0",
  "answers": { "has-validity-issues": { "type": "noul", "noul": 0.2 } },
  "usage": { "input_tokens": 303, "output_tokens": 27,
             "cost_usd": 0.000128, "credits_remaining_usd": 9.955148 }
}
```

### レスポンス例（choice）— confidence と全選択肢の確率が返る

```json
{
  "answers": { "domain": {
    "type": "choice", "choice": "security", "confidence": 0.93,
    "probabilities": {"concepts": 0, "tech": 0.05, "security": 0.95, "billing": 0}
  }}
}
```

### レスポンス例（score）— legend 付きでスペクトラム上の位置が返る

```json
{
  "answers": { "diff": {
    "type": "score", "score": 0.76, "confidence": 0.6,
    "legend": {"0": "とても易しい", "1": "標準", "2": "非常に難しい"},
    "probabilities": {"0": 0.25, "1": 0.74, "2": 0.01}

}
```

## 2. 強み（すべて実測）

### ① 安い・速い

$0.0008/問、並列6で90問15秒。LLMに同じ判断をさせるのと桁が違う。
**残高がレスポンスに入っている**ので予算管理が容易（`credits_remaining_usd`）。

### ② 表層的・パターン的な判定は強い

選択肢に不要な括弧補足（略語展開・定義文）が混入しているかの判定:

```
hint_leak: AUC 0.901  （閾値0.3 で P=0.75 / R=0.93）   →追試で訂正: n=45 の楽観値。n≈190 で 0.82
```

素朴な正規表現（括弧の有無を数えるだけ）と同一サンプルで比較すると、**Jevが僅差で勝つ**（→追試で訂正: 強化した静的ルールとはほぼ同等。§6b）:

| 手法 | P | R | コスト |
|---|---|---|---|
| 正規表現（括弧の有無） | 0.667 | 0.878 | 0 |
| **Jev hint_leak（0.3）** | **0.750** | **0.933** | $0.0003/問 |

正規表現が勝てない理由: ok判定された問題の33.3%も括弧を持っている。
`（12シャード）`のような技術的な量は正当で、`（エンベロープ暗号化）`のような
略語展開は不当。**この区別は意味判断であり、Jevはそれができる。**

### ③ 構造化された確率が返る

閾値運用・ランキング・argmax が可能。テキストのパースが不要で、
`choice` は全選択肢の確率分布まで返す。

### ④ 1コールに複数質問を束ねられる

観点ごとに質問を分けても1リクエストで済む（ただし後述の希釈に注意）。

## 3. 弱み（すべて実測）

### ① 深い事実推論ができない ← 最重要

「この問題の正解は本当に正しいか」＝AWSの仕様を推論して検算する問い:

```
answer_wrong: AUC 0.446 → 公式作法で書き直して 0.473
```

**0.5がランダム。つまり全く機能しない。**

これがプロンプトの問題でないことは**対照実験で確定**させた。
同じ作法で書いた hint_leak は 0.886 → 0.901 に改善している（n=45。→追試で訂正: この差は誤差の範囲で、作法の効果は確認できていない。`answer_wrong` が 0.47 でランダム同等という点は変わらない）。
**作法は正しく効いているのに answer_wrong は動かない＝能力限界。**

### ② 曖昧な質問で崩壊する

```
any_issue（「何か妥当性の問題があるか」）: AUC 0.425
```

**ランダムより悪い**（わずかに逆相関）。複数観点をORで詰め込むと出力が平均化する。

### ③ 非決定的

同一入力を2回実行した差（n=24）:

```
中央値 0.010 / 平均 0.017 / 90%点 0.020 / 最大 0.110
```

大半は安定だが外れ値がある。**閾値で合否を決める用途には不適。**

### ④ confidence が信頼できない

`choice` でドメイン分類させたときの誤分類例:

```
conf=0.96  正解「検出」          → 予測「インシデント対応」
conf=0.92  正解「脅威・脆弱性」   → 予測「認証・認可」
```

**自信たっぷりに間違える。** confidence で絞っても一致率は92.7%が上限だった。

### ⑤ 質問を詰め込むと希釈される

同じ hint_leak の AUC:

| 構成 | AUC | 測定 |
|---|---|---|
| 1質問・選択肢だけのstate | 0.886 | n=45 |
| 3質問・構造化state | 0.901 | n=45 |
| 6質問・大きなstate（ドメイン一覧込み） | 0.574 | **n=20（誤差が大きい）** |

**追試で訂正**: 上の3行は標本が小さく、差を語れない。n≈190×2 で測り直した同じ比較が次。

| 構成 | AUC（プール） |
|---|---|
| 2質問を1コール・全state（問題文・解説込み） | 0.776 |
| **1質問・選択肢だけ** | **0.819**（差 **+0.043 [+0.011, +0.075]**、P=0.995） |

**質問を詰める・不要なstateを渡すと希釈される**という方向は追試でも確認できた。ただし
「0.901→0.574」のような大きな落ち込みは、n=20 の誤差を含む過大な値。実際の差は +0.043。

### ⑥ 判定はできても修正はできない

生成しないモデルなので当然だが実務上重要。しかも
**「検出できるから機械的に修正できる」も成立しない**:

実際の修正前後148件に機械的な括弧除去を当てた一致率は **選択肢単位で72.6%**
（問題単位の完全一致は46.6%）。機械適用すれば半数以上を壊す。

| before | 機械的除去 | 実際の正しい修正 |
|---|---|---|
| `シャード数を3倍（12シャード）に増やし` | 削除 | **保持**（技術的な量） |
| `累積スナップショットファクト（要件①）` | 削除 | **保持**（参照記号） |
| `リホスト（Rehost）：…移す戦略` | 削除 | **`リホスト（Rehost）` に短縮** |

## 4. 観点別の実測AUC一覧

positive/negative 各45件・現行ルール下のラベル（`validityCheckedAt >= 2026-08-20`）。
**追試（n≈190×2・domain補完の正例を除外）の値を右列に併記した。記事には右列を使う。**

| 観点 | AUC（第1ラウンド n=45） | 追試で訂正 | 判定 |
|---|---|---|---|
| 選択肢の括弧ヒント漏れ（hint_leak） | 0.901 | **0.82** | ✅ 採用（選択肢のみ・単独コール） |
| 選択肢別解説のズレ（ce_misaligned） | 0.750（P=0.90 / R=0.40） | 0.60（ズレ欠陥のみ対象） | ❌ 採用せず |
| 事実誤り（factual_error） | 0.643 | 0.64（変わらず） | ❌ **寄与しなかったので外した**（足しても改善しない） |
| 正解の当否（answer_wrong） | **0.473** | ❌ ランダム同等 |
| 曖昧な総合質問（any_issue） | **0.425** | ❌ ランダム以下 |
| ドメイン誤り（domain_wrong） | ※下記 | ❌ |

### ドメイン誤りについて（ラベルリークの注意書き付き）

当初 **AUC 1.000** が出たが**ラベルリーク**だった。
domain修正66件のうち **62件は `None → int`（未設定の補完）**で、
Jevは「フィールドが空である」ことを検出していただけ。真の誤分類は4件のみ。

正しく測り直した結果（ok判定済み70件で分類の一致率）:

| 手法 | 一致率 | 誤り検出のP |
|---|---|---|
| noul を並べて argmax | 85.1% | 0.286 |
| **choice タイプ（正しい道具）** | **87.1%** | **0.308** |

正しい道具を使っても結論は変わらず、**ドメイン判定はJevに任せられない**。
不一致は「モニタリング vs セキュリティ」のような本質的に曖昧な境界だった。

## 5. 質問の書き方（公式実装の作法）

`jev-skills/src/jev/questions.ts` の `fullQuestion` に倣う。

```python
{
  "state": {                       # ← 名前付きキーの構造体
    "certification": "DVA",
    "question_text": "...",
    "choices": ["...", "..."],
    "explanation": "...",
  },
  "questions": {
    "hint_leak": {
      "type": "noul",
      "instructions": {            # ← 散文ではなく構造化
        "role": "You are auditing the answer choices of ...",
        "question": "Does any entry of `choices` contain ...",   # ← stateのキーを参照
        "not_a_defect": "A concrete technical quantity such as '(12 shards)' ...",
      },
      "criteria": {                # ← true/false の境界を明示
        "true": "At least one choice carries an explanatory parenthetical.",
        "false": "Every choice is the bare term, with no explanatory parenthetical.",
      },
    }
  }
}
```

ポイント:
- `state` のキーを質問文から **`` `backtick` ``** で参照する
- `criteria` で true と false の意味を書く（これがないと境界が決まらない）
- **反例（`not_a_defect`）を書くと精度が上がる。** 「何が欠陥でないか」の明示が効く

## 6. 実運用への活かし方（最終設計）

### 役割分担

| 担当 | 仕事 | 根拠 |
|---|---|---|
| **Python** | 構造的不整合の検出（欠損・件数不一致・空フィールド） | 決定的・無料・確実 |
| **Jev** | 「どれを先に見るか」の順位付けのみ | AUC 0.82 / $0.0003/問（→追試で更新。旧 0.775 / $0.0008） |
| **Claude** | 意味的な検証と**すべての修正** | 正解の当否はJev AUC 0.473＝不可 |

### なぜ「ゲート」ではなく「順位付け」なのか

ゲート（Jevが問題なしと言えばClaudeをスキップ）として使うと:

| 閾値 | Recall | Claudeへ送る率 |
|---|---|---|
| 0.30 | 0.950 | 73.3% |
| 0.50 | 0.733 | 50.0% |

recall 0.95 でも**節約は27%**。しかも取り逃した3件が「事実誤り」「解説のズレ」
＝**まさにゲートが存在する理由**だった。

一方、対象の夜間バッチは**トークン律速でそもそも全問回せない**。
ならば「処理するか否か」ではなく**「どれを先に処理するか」**に使えばよい。

**この用途なら recall 不足が品質リスクにならない**（低スコアの問題も後日必ず処理される）。
Jevが落ちても順序が変わるだけで何も壊れない。

### 最終的な選定順位

```
① 未確認（未検証＝アプリ非公開）を常に最優先・古い順
   └ 未確認だけで枠が埋まるならJevを呼ばない（費用ゼロ）
        ↓ 残り枠があれば
② 確認済みから プール = 古い順の上位（残り枠×3）をJevがスコア化
   └ スコアの5段階バンド降順 → 同一バンド内は確認日の古い順
```

設計上の要点:

- **飢餓対策**: プールを「古い順の上位N×倍率」で切る。全体をスコア順にすると
  低スコアの問題が永久に選ばれない
- **バンド化**: 連続値のままだと 0.94 と 0.93 の差で順序が決まり日付が効かない。
  バンド幅はノイズより粗くする必要がある（実測でバンドが揺れる率 0.1→17% / 0.25→**4%**）。
  →追試で訂正: 精度面では粗くする必要はない（ノイズを均しても AUC は変わらない）。
  粗い帯は「日付優先」のための設計上の代償で、欠陥検出を 1 バッチあたり約 1.7 件（探索）落とす
- **縮退**: APIキー未設定・通信不能・レスポンス不正・予算超過の4系統すべてで
  従来の古い順にフォールバックすることを実測確認
- **ロックを保持しない**: ネットワークI/O中に排他ロックを持つと並列実行を数分止める

### 効果

| 項目 | 旧（第1ラウンド） | 訂正後（追試） |
|---|---|---|
| トリアージ指標 | `max(hint_leak, factual_error)` | **`hint_leak` 単独**（選択肢のみを渡す） |
| 実測AUC（実物で検証） | 0.775（n=45） | **0.82**（プール）/ 未見データの実物で **0.833** |
| 1バッチあたりの欠陥検出 | 約1.6〜1.7倍 | **約1.7〜1.8倍**（帯0.25。連続値なら 1.8〜1.9倍） |
| コスト | $0.0008/問・$0.072/バッチ・約$2.2/月 | **$0.0003/問・約$0.03/バッチ・約$0.8/月** |

改善の中身: 質問を分離して state を選択肢だけに絞る。プールした差は **+0.043 [+0.011, +0.075]**、
探索・未見の両方で同じ +0.042 が再現した。費用は 63% 減。
**第1ラウンドの設計は「効かない質問を混ぜ、全 state を渡して希釈していた」＝「Jevの使い方」が悪かった。**

## 6b. 追試: Jev は静的解析で代替できるか（2026-09-30）

きっかけは「Jev の意味はある？ 静的解析では無理なこと？」という問い。
第1ラウンドの正規表現との比較は、括弧の有無を数えるだけの素朴な版が相手だった。
静的側にも同じ手順（設計→探索→未見）を踏ませて比べ直した。

静的ルール（1行）: **数字を含まない括弧を持つ選択肢の割合**
（数量 `（12シャード）` や参照記号 `（要件①）` は正当なので除く）。

### 全体の AUC

| | 探索 | 未見 |
|---|---|---|
| Jev（選択肢のみ・1質問） | 0.803 | 0.836 |
| 静的: 数字なし括弧率 | 0.780 | 0.778 |
| 静的: 略語展開／定義らしさ | 0.745 | 0.788 |
| 静的: 括弧率（有無だけ） | 0.765 | 0.758 |

Jev − 数字なし括弧率（プール）= +0.014〜+0.066（P=0.999）。**Jev が統計的に上だが、差は約 +0.04 と小さい。**
重みを学習させた静的ルールが相手だと、未見で +0.030 [−0.004, +0.068]（有意でない）。

### 括弧がある問題だけで比べる（静的解析が苦手なはずの領域）

括弧の有無では決まらない領域で、ヒント漏れ（positive）と正当な括弧（negative）を切り分けられるか。

| | 探索 | 未見 |
|---|---|---|
| **Jev** | **0.785** | **0.749** |
| 静的: 数字なし括弧率 | 0.735 | 0.595 |
| 静的: 略語展開／定義らしさ | 0.689 | 0.666 |
| 静的: 括弧率 | 0.652 | 0.473 |

Jev − 数字なし括弧率（プール）= **+0.032〜+0.171**（P=0.998）。**ここは Jev の本物の優位。**
括弧率（有無だけ）は未見で 0.473＝ランダム以下。

### 運用での効果（1バッチ＝プール90問から30問。ランダムなら11.4件）

| 欠陥検出数/バッチ | 探索 帯0.25 | 探索 帯0.1 | 未見 帯0.25 | 未見 帯0.1 |
|---|---|---|---|---|
| Jev | 19.0 | 20.5 | 21.0 | 21.9 |
| 静的: 数字なし括弧率 | **20.2** | 20.5 | **20.2** | 20.2 |

- **帯0.25（日付優先を保つ現行設定）では差なし**（平均 Jev 20.0 対 静的 20.2）。
- 帯0.1 以下にすると Jev が平均 +0.8 件（約4%）上回る。
- Jev と静的を平均しても Jev 単独より良くならない（未見 −0.016）。

### 結論

**Jev が優れていた点**（すべて実測）:

1. 括弧のある問題の中で「ヒント漏れ」と「正当な括弧」を切り分けられる（AUC 0.75〜0.79 対 静的 0.60〜0.74）。
   ルールを書かずに、曖昧な境目を判断できる。
2. 最初の1質問・数行の指示で AUC 0.80 に届く。特徴設計が要らない（これは測定ではなく作業の実感）。
3. 安い・速い（$0.0003/問、186問が40秒）。確率と費用が構造化されて返る。

**Jev が優れていなかった点**:

1. **静的解析では無理なことを、Jev もできていない。** 意味的な欠陥（事実誤り 0.64・正解の当否 0.47・
   解説のズレ 0.55〜0.60）は Jev も判定できない。当初の構想「静的でできない確認を Jev に任せる」は成立しなかった。
2. **今回の用途（トリアージ）では、静的な1行ルールでほぼ同じ運用結果が出る。** 効果の大半は
   「怪しい順に並べる」発想から来ていて、手段が Jev か静的かは二次的だった。

残る判断: **A. 静的ルールに置き換える**（外部依存・費用・非決定性がなくなる）か、
**B. Jev を残す**（帯を細かくすれば +4%、日付優先は弱まる）か。**未決定。**

限界: 静的ルールの考案は探索データを見た後（ただし探索 0.780 → 未見 0.778 と再現）。
欠陥検出数の差（約1件/バッチ）は誤差に近い。ラベルは Claude の判定でノイズを含む。

## 7. 記事にする際の軸（提案）

### 追試後の軸（こちらを推す）

**「新しい道具を試したら役に立った」ではなく、「道具を外しても同じ結果が出るか」まで確かめた話。**

筋:

1. Jev を実運用に入れる。当初の構想は「静的でできない確認を Jev に任せる」。
2. 測ると成立しない（意味的な欠陥は Jev も判定できない）。用途を「確認」から「順位付け」へ変えて着地。
3. 精度も改良（質問を分離して state を絞る。AUC +0.043、費用63%減）。ここまでは成功談。
4. しかし**静的な1行ルールでほぼ同じ運用結果が出る**。効果の出どころは道具ではなく
   「怪しい順に並べる」という発想だった。

Jev の位置づけ（誇張しない）:

- 本物の強みは、**静的ルールが苦手な曖昧な境目（正当な括弧 対 ヒント漏れ）を、ルールを書かずに
  切り分けられる**こと。ただしこの優位は、現行の運用設定では欠陥検出数にほとんど出ない。
- 良いモデルだが、**自分の用途では必須ではなかった**。これは失敗談として価値がある。
- 読者への問い: 「その道具でなければできないことは何か」「比較相手（静的）に同じ努力を払ったか」。

注意: 静的に置き換えるか Jev を残すかは**未決定**。決まったら §6b に追記する。記事に書く前に確認すること。

### 追試前の軸（参考として残す）

**「System One に System Two の仕事をさせようとして失敗し、System One の仕事に
置き換えたら実用になった」** という一本の線で書けば、強み弱みが自然に説明できる。
（→追試後は、この「実用になった」部分にも「静的でも同じ」という但し書きが付く。）

- Jev は「速い直感」を売りにしたモデル（System One）。
  直感で答えられる問いには強く、熟考が要る問いには使えない。**コンセプト通り。**
- 失敗したのはモデルではなく、**期待のかけ方**だった。
- 「確認＝判断だからJevに任せられる」と考えたが、実は確認の中に
  **表層の判断（Jev可）と熟考（Jev不可）が混ざっていた**。
  分解して初めて、どこまで任せられるかが分かった。

### 読者に持ち帰ってもらう教訓

1. 曖昧な質問は機能しない。観点ごとに分解し `criteria` で境界を示す
2. 評価には対照群を置く。でないと「プロンプトが悪い」のか「能力不足」か切り分けられない
3. AUC 1.000 を疑う。欠損値の補完が混ざったログは簡単にリークする
4. 検出と修正は別の難しさ。検出できても機械的に修正できるとは限らない
5. SDKの型定義をモデルの能力と混同しない。一次情報を見る
6. 非決定的なモデルを閾値の合否判定に使わない。ランキングなら安全
7. **同じ精度でも用途を変えれば実用になる。** recall不足が害にならない設計に寄せる
8. **自分の提案にも対照を置く。** 比較相手（静的）に同じ努力を払わないと、勝って見えるだけ
9. **効果の出どころを分解する。** 今回は「怪しい順に並べる」発想が効果の大半で、手段（Jev）は二次的だった
10. **評価データに「もう存在しない欠陥」が混ざっていないか確認する。** 2度踏んだ（domain 補完）
11. **改良案は事前に1つに固定し、未見データで現行と比べる。** 事後に選ぶと偽の改善が出る（abbr は 0.68→0.54）
12. **n=45 の AUC は差を語れない。** 必ず信頼区間を付ける
13. **「新しい道具を使った」と「問題が解けた」は別。** 道具を外しても同じ結果が出るかを確かめる
