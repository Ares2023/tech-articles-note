# 調査ログ: Jev を妥当性チェックに使えるか

調査日: 2026-09-30
対象: Mugenknock（`/home/yuzuki/aws-quiz-app`）の夜間バッチ `02-check-validity.sh`
Jev 消費: **$0.67**（全11フェーズの実測込み・残高 $9.29）

追記型。却下した案も消さない。

---

## 0. 動機

`02-check-validity.sh` は DynamoDB の問題（4,895件）を順に読み、Claude に
「事実誤り・整合性の破れがないか」を確認させ、**問題があればその場で修正まで**させる
夜間バッチ。品質ゲートで、未検証の問題はアプリに公開されない。

これが**トークン律速で回らず、2026-06-29 から夜間バッチの実行リストでコメントアウトされている**
（hook経由では動いている）。

そこで当初の構想:

> **確認は Jev（安い・速い）、修正は Claude（賢い）に分業すれば、同じトークンで
> もっと多くの問題を回せるのではないか。**

これを実データで検証した記録。

## 1. まず現状を測る（Jevを触る前）

Jev を試す前に「そもそも節約の余地があるか」を確認した。過去39回分の実行ログを集計:

```
総問題数 755
ok:     468 (62.0%)
fix:    287 (38.0%)
delete:   0 (0.0%)
```

**38%が要修正**。つまり完璧なプリフィルタがあっても Claude 呼び出しは62%削減が上限。
悪くない余地はある。

次に fix の内訳（287件の理由を分類）:

| 割合 | 内容 |
|---|---|
| 63.2% | 選択肢への略語展開・括弧補足の混入 |
| 52.1% | choiceExplanations の不足・ズレ・件数不一致 |
| 42.7% | correctAnswers が choices と不一致 |
| 21.9% | ドメイン（出題分類）の誤り |
| 12.5% | isMultiple フラグの不整合 |
| **3.8%** | **事実誤り・サービス仕様の誤り** |

→ **「事実誤り」は3.8%しかなく、大半が機械的・表層的なパターン**だった。
この時点の仮説は「LLMもJevも要らない。正規表現で済むのでは？」

### 決定的ルールを全4,895件に当てた結果

```
choice_paren（選択肢に括弧）: 2,240件 (45.8%)
domain_missing:                  2件
correct_not_in_choices:          0件
ce_count_mismatch:               0件
isMultiple_mismatch:             0件
```

構造的な不整合は**すべて0件**＝既に解消済み。残る論点は「選択肢の括弧」だけ。

ただし重要な発見: **ok判定された問題の33.3%も選択肢に括弧を持っていた。**
つまり「括弧があれば欠陥」ではなく、**正当な括弧と不当な括弧を区別する判断**が必要。
ここでようやく「単純な正規表現では無理」＝判定モデルの出番がある、と分かった。

## 2. 【失敗①】曖昧な質問は機能しない — AUC 0.425

最初の実装（`jev-validity-eval.py` の初版）は、単一の質問を投げるものだった:

```
"Does this AWS certification exam question have validity issues requiring review
 or correction? Issues include: wrong correct answer, answer text not matching
 choices, factual errors about AWS service specifications, ..."
```

結果: **AUC 0.425**。0.5がランダムなので、**ランダムより悪い**（わずかに逆相関）。

pos平均 0.328 / neg平均 0.360 で、欠陥がある問題のほうが**低い**スコアを返していた。

### なぜ失敗したか

「何か問題があるか」という問いは、Jev にとって**判断基準が決まらない**。
複数の観点をORで詰め込んだため、どの観点で見るべきか決められず出力が平均化した。

→ 方針転換: **観点ごとに独立した具体的な質問に分解する。**

## 3. ラベル設計の罠

評価の前にラベルを作る必要がある。設計:

- positive: `validityEditLog` があるもの（Claudeが修正した）→ `changes.*.before` で修正前の状態に復元
- negative: `validityEditLog` がないもの（Claudeがokと判定した）

ここに罠があった。**選択肢の括弧ルールは 2026-08-20（コミット e5b3630）に追加されたもの。**
それ以前に「ok」と判定された問題は、現行ルールでは要修正でありうる。

→ `validityCheckedAt >= 2026-08-20` で限定。結果 positive 458件 / negative 817件。
この限定をしないと negative にノイズが混ざり、AUC が不当に低く出る。

**教訓: ルールが変わるシステムのログをラベルにするときは、ルール確定日でカットする。**

## 4. 観点を分解して測り直す

6つの具体的な質問に分解して1コールに束ね、positive/negative 各60件で測定。

| 質問 | AUC | 分離度 |
|---|---|---|
| hint_leak（選択肢の括弧ヒント漏れ） | 0.753 | +0.269 |
| factual_error（事実誤り） | 0.573 | +0.018 |
| domain_wrong（ドメイン誤り） | 0.551 | +0.058 |
| ce_misaligned（解説のズレ） | 0.485 | +0.017 |
| answer_wrong（正解の当否） | 0.446 | −0.007 |
| any_issue（曖昧な質問・対照） | 0.425 | −0.031 |

hint_leak だけが機能。他は軒並みランダム付近。

## 5. 【気づき】AUCを「全positive」で測ると希釈される

上の表は各質問を**全positive**に対して測っている。しかし hint_leak は
「選択肢の括弧」を見る質問なので、解説のズレしかない問題に対して低いスコアを返すのは**正しい**。

→ 欠陥カテゴリ別に測り直した（その質問が担当する欠陥を持つpositiveのみ vs 全negative）:

| 欠陥カテゴリ | n | 対応質問 | AUC |
|---|---|---|---|
| choices | 41 | hint_leak | **0.858** |
| domain | 9 | domain_wrong | **0.978** |
| explanation | 16 | factual_error | 0.729 |
| choiceExplanations | 28 | ce_misaligned | 0.614 |

数字が一気に良くなった。**評価は「その検出器が担当する欠陥」に対して測らないと不当に低く出る。**

## 6. 【失敗②】AUC 1.000 の幻 — ラベルリーク

domain_wrong を n=45 で追試したら **AUC 1.000**（閾値0.5でP=1.000/R=1.000、完全分離）。
狂喜した。1問 $0.00033 で完璧にドメイン誤りが検出できる、と。

疑って中身を見た。**domain修正66件のうち62件が `before=None → after=int`**。
つまり「ドメインが誤っていた」のではなく**「ドメインが未設定だった」**問題だった。

復元処理が `domain` を `None` に戻すので、Jev には
`ASSIGNED DOMAIN: None. (unset/out of range)` が渡っていた。
**Jev は「フィールドが空である」ことを検出していただけ。**
これは `if q.get('domain') is None` で無料・確実にできる。

真の誤分類（int→int）は **4件しかなかった**。

### 正しく測り直す

ok判定済み70件（＝現在のドメインが正しいというground truth）で、Jevのargmax一致率を測定:

```
argmax 一致率: 85.1%
不一致を「誤り」とみなすと P=0.286（14件flagして10件が誤検出）
confidence 0.9以上に絞っても一致率97.1%（採用率45.9%）
```

→ **ドメイン判定はJevに任せられない。** 不一致例は
「モニタリング vs セキュリティ」のような本質的に曖昧な境界だった。

**教訓: AUC 1.000 が出たら喜ぶ前にラベルリークを疑う。
とくに「欠損値の補完」が混ざったログをラベルにすると簡単にリークする。**

## 7. 公式実装の作法を読む → 対照実験

`~/.claude/plugins/marketplaces/jev-skills/src/jev/questions.ts` を読んだら、
自分の使い方と3点違っていた:

1. `instructions` は散文の文字列ではなく**構造化オブジェクト**
2. `state` も**名前付きキーの構造体**で、質問側からバッククォートで参照（`` `request` ``）
3. **`criteria: {true, false}`** で true/false の意味を明示

この作法で、最重要だった `answer_wrong` と `factual_error` を再測定。
**対照として hint_leak も同じ作法で測った**（作法の効果を切り分けるため）。

| 質問 | 旧 | 構造化+criteria | 変化 |
|---|---|---|---|
| answer_wrong | 0.446 | **0.473** | +0.027 |
| factual_error | 0.729 | 0.643 | −0.086 |
| **hint_leak（対照）** | 0.886 | **0.901** | +0.015 |

**対照の hint_leak が改善したことが決定的だった。** 作法の実装は正しく効いている。
それでも answer_wrong が 0.473 に留まる＝**プロンプトの書き方の問題ではなく能力限界**。

対照群がなければ「まだプロンプトが悪いのかも」と延々チューニングしていた。

**教訓: 「使えない」と結論づける前に、必ず「使えるはずの観点」を同条件で測る。**

## 8. 【失敗③】SDKの制約をAPIの制約と誤認

`src/jev/client.ts` を見ると型が `type: "noul"` のみ:

```typescript
export type Noul = { type: "noul"; instructions: unknown; criteria?: {...} };
const NoulAnswer = z.object({ type: z.literal("noul"), noul: z.number() });
```

→ 「Jevはカテゴリを直接出力できない」と判断し、**ドメインごとにnoul質問を並べてargmaxを取る**
回避策を実装した。

後日（記事プロジェクトの既存 overview.md を読んで）**`choice` と `score` タイプが
公式に存在する**ことを知る。APIで直接叩いて確認:

```json
{"type":"choice","choice":"security","confidence":0.93,
 "probabilities":{"concepts":0,"tech":0.05,"security":0.95,"billing":0}}
```

**動く。** つまり制約は**プラグインSDKの実装範囲**であって、APIの制約ではなかった。

### choice で測り直した結果

| 手法 | ok判定の一致率 | 誤り検出のP |
|---|---|---|
| noul を並べてargmax（回避策） | 85.1% | 0.286 |
| **choice タイプ（正しい道具）** | **87.1%** | **0.308** |

**結論は変わらなかった**（+2ポイント）。ただし重要な副産物を得た:

**confidence は信頼できない。** 誤分類例に conf **0.92** / **0.96** のものがあった。
自信たっぷりに間違える。confidenceで絞っても一致率は92.7%が上限だった。

**教訓: SDKのラッパーの型定義を、モデル本体の能力と混同しない。一次情報（APIドキュメント）を見る。**

## 9. 正規表現との直接対決

hint_leak は結局「括弧の検出」。無料の正規表現に勝てるのか、同一サンプルで比較:

| 手法 | P | R | コスト |
|---|---|---|---|
| 正規表現（選択肢に括弧あり） | 0.667 | 0.878 | **0** |
| Jev hint_leak（閾値0.3） | 0.750 | 0.933 | $0.0003/問 |

Jevが僅差で勝つが、正規表現がほぼ追いつく。

### しかし決定的な発見は別だった

「検出できるなら、修正も正規表現でできるのでは？」と考え、
実際の `before → after` 148件に機械的な括弧除去を当てて一致率を測った:

```
選択肢単位の一致: 432/595 (72.6%)
問題単位で全選択肢一致: 69/148 (46.6%)
```

不一致の中身を見ると、判断が完全に意味依存だった:

| before | 機械的除去 | Claudeの実際の修正 |
|---|---|---|
| `シャード数を3倍（12シャード）に増やし` | 括弧を削除 | **そのまま保持**（技術的な量は欠陥でない） |
| `累積スナップショットファクト（要件①）` | 括弧を削除 | **そのまま保持**（参照記号） |
| `リホスト（Rehost）：アプリケーションを…そのままクラウドへ移す戦略` | 括弧を削除 | **`リホスト（Rehost）` に短縮**（括弧を残し定義文を削除） |

→ **機械適用すれば半数以上の問題を壊す。修正は必ずClaudeでなければならない。**
「検出」と「修正」は別の難しさを持つ、という当たり前だが実務上重要な線引きが確認できた。

## 10. 【方針転換】ゲートではなくランキングに使う

ここまでで分かったこと:
- Jevが確実に使えるのは hint_leak（AUC 0.901）だけ
- ゲートの存在理由である意味的欠陥（正解の誤り・事実誤り）は検出できない

ゲート（Jevが「問題なし」と言ったらClaudeをスキップ）として使うと:

| 閾値 | Recall | Claudeへ送る率 |
|---|---|---|
| 0.30 | 0.950 | 73.3% |
| 0.40 | 0.833 | 59.2% |
| 0.50 | 0.733 | 50.0% |

recall 0.95 を確保しても**節約は27%**。しかも取り逃した3件を見たら:

```
mla-c1f29f55  explanation: SHAPが未展開
saa-eed6a38c  choiceExplanations: 2肢が同一文で固有の根拠になっていない
scs-10eca45e  choices+explanation: Conformance Packへの虚偽説明文が埋め込まれていた
```

**まさにゲートが存在する理由そのもの**を取り逃していた。ゲートには使えない。

### 転換

**02 はそもそもトークン律速で全問回せない**（だから停止中）。
ならば「処理するか否か」ではなく**「どれを先に処理するか」**をJevに決めさせればよい。

この用途なら:
- recall不足が品質リスクにならない（低スコアの問題も後日必ず処理される）
- 同じトークン量で見つかる欠陥の数が増える
- Jevが落ちても順序が変わるだけで何も壊れない

指標の最適な組み合わせを探索（domainリークを除いた実運用値）:

```
max(hint_leak, factual_error)             AUC 0.763  ← 採用
max(hint_leak, ce_misaligned, factual)    AUC 0.763
mean(hint_leak, ce_misaligned)            AUC 0.762
hint_leak 単独                             AUC 0.753
```

※ 当初 `+domain_wrong` で AUC 0.825 が出ていたが、これはリーク込みの値。除外して0.763が実力。

## 11. 実装時に踏んだ罠

### 飢餓（starvation）

全体をスコア順に並べると、**低スコアの問題は永久に選ばれない**。
→ プールを「古い順の上位 N×倍率」に限定。全問が必ず順番にプールへ上がる性質を保つ。

### 非決定性

同一入力で2回実行して差を測定（n=24）:

```
中央値 0.010 / 平均 0.017 / 90%点 0.020 / 最大 0.110
```

大半は安定だが外れ値がある。**閾値で合否を決める用途には使えない**理由がここにも。

### 浮動小数点

スコアをバンドに丸める実装で `int(0.70 / 0.1)` が **6** になった（6.999…の切り捨て）。
バンド境界が静かに1つずれる。`+1e-9` で修正。テスト出力を目視して気づいた。

### バンド幅の決定

「同程度に疑わしいものの中では古い順」を成立させるには、バンドがノイズより十分粗い必要がある。
実測:

| バンド幅 | バンドが揺れる率 | バンド数 |
|---|---|---|
| 0.1 | 17% | 11 |
| 0.2 | 12% | 6 |
| **0.25** | **4%** | **5** |
| 0.34 | 0% | 3 |

→ 0.25（5段階）を採用。細かく刻むとノイズで順序が入れ替わるだけで日付が効かなくなる。

### ロックの保持

クレーム（並列実行の競合防止）は flock で排他している。トリアージをロック内で呼ぶと
**ネットワークI/O中に他プロセスを数分ブロックする**。
→ ロック外で実行し、権威的な除外は従来どおりロック内で行う二段構成にした。

## 12. 最終的な設計

```
① 未確認（validityCheckedAt なし）を常に最優先・古い順
   └ 未確認はアプリ非公開。公開までの時間を最短化するのが最優先
   └ 未確認だけでバッチが埋まるならJevを呼ばない（費用ゼロ）
        ↓ 残り枠があれば
② 確認済みから プール = 古い順の上位（残り枠×3）をJevがスコア化
   └ スコアの5段階バンド降順 → 同一バンド内は確認日の古い順
        ↓
   残り枠の分だけClaudeへ（Claudeに渡す総数は従来と同じ）
```

役割分担の最終形:

| 担当 | 仕事 | 根拠 |
|---|---|---|
| **Python** | 構造的不整合の検出（欠損・件数不一致） | 決定的・無料・確実 |
| **Jev** | 「どれを先に見るか」の順位付け | AUC 0.775・$0.0008/問 |
| **Claude** | 意味的な検証と**すべての修正** | 正解の当否はJev AUC 0.473＝不可 |

### 効果

| 項目 | 値 |
|---|---|
| トリアージのAUC（実物で検証） | 0.775 |
| 1バッチあたりの欠陥検出 | **約1.6〜1.7倍** |
| コスト | $0.0008/問・$0.072/バッチ・約$2.2/月 |

### 縮退設計（4系統を検証）

APIキー未設定 / 通信不能 / レスポンス不正 / 予算超過（120秒）
→ すべて空スコア+exit 0 で、**従来の古い順に完全一致でフォールバック**することを実測確認。

## 却下した案

| 案 | 却下理由 |
|---|---|
| Jevをゲート（合否判定）にする | recall 0.95で節約27%。取り逃しが事実誤り・解説ズレという致命的な種類 |
| 正規表現で括弧を機械的に除去 | before→after一致率72.6%。半数超を壊す |
| Jevにドメイン分類させる | choice型でも一致率87.1%・誤検出P=0.308。confidence 0.96で誤る |
| `answer_wrong` をトリアージ指標に入れる | AUC 0.473。ノイズになるだけ |
| `any_issue`（曖昧な総合質問） | AUC 0.425でランダム以下 |
| 全体をJevスコア順に並べる | 低スコア問題が永久に選ばれない飢餓 |
| 質問を6つ全部1コールに束ねる | 希釈でhint_leakが0.901→0.574に劣化 |

## 一般化できる教訓（記事の核）

1. **Jevは「System One（速い直感）」。** 直感で答えられる問い（表層パターン）には強く、
   熟考が要る問い（AWS仕様を推論して正解を検算する）には使えない。
   コンセプト通りの性能であって、期待のかけ方を間違えたのは使う側。
2. **曖昧な質問は機能しない。** 「何か問題があるか」はAUC 0.425。
   観点ごとに分解し、`criteria` で true/false の境界を示す。
3. **評価には必ず対照群を置く。** 対照がなければ
   「プロンプトが悪いのか能力が足りないのか」を切り分けられない。
4. **AUC 1.000 を疑う。** 欠損値の補完が混ざったログをラベルにすると簡単にリークする。
5. **検出と修正は別の難しさ。** 検出できても修正できないことがある。
6. **SDKの型定義をモデルの能力と混同しない。** 一次情報を見る。
7. **非決定的なモデルを閾値の合否判定に使わない。** ランキングなら安全に使える。
8. **recall不足が害にならない設計に寄せる。** 同じ精度でも、用途を変えれば実用になる。

## 13. 精度は上げられるか — n を増やして測り直す

### 13.0 なぜ測り直したか

第12節の AUC 0.775 は positive/negative 各45件の値。ブートストラップで95%信頼区間を取ると
±0.1 あり、「改善した／しなかった」を語れる精度ではなかった。そこで次の手順にした。

- **探索データ**: 100件 / 100件。改善案を試す母集団。
- **未見データ**: 別の100件 / 100件（探索と重複0件）。**事前に1候補を固定してから**現行と比較する。
- すべての AUC に95%CI、比較はペア・ブートストラップ。
- 生データとスクリプトは `aws-quiz-app/prompts/night-prompts/scripts/jev-experiments/2026-09-30/` に保存。

### 13.1 【失敗④】正例に「もう存在しない欠陥」が混ざっていた

第6節の AUC 1.000（ラベルリーク）と同じ根を、もう一度踏んだ。

正例の約13%（200件中12件）は、修正理由が「ドメイン未設定の補完（`None → int`）」だった。
これは本番のプールにはもう存在しない欠陥種で、評価を両方向に歪める。

- Jev には domain が見えない → Jev の AUC が**不当に低く**出る
- 決定的特徴（`domain_missing`）には自明 → 静的側の AUC が**不当に高く**出る

除外すると数字が動いた。

| | 除外前 | 除外後 |
|---|---|---|
| 現行Jev（2問・全state）のAUC | 0.695 | 0.761 |
| 決定的特徴のみ（CV-AUC） | 0.777 | 0.758 |
| Jev＋決定的特徴（CV-AUC） | 0.823 | 0.794 |

一時は「決定的特徴と組み合わせれば現行比 +0.127」と見えたが、これは水増しで、

## 14. Jev の値を Claude のプロンプトに渡す

依頼: Jev で確認済みの問題は、Claude に渡す妥当性確認プロンプトにその値を渡し、
「どのくらい怪しいか」の指標にしたい。

実装: Jev が判定した問題にだけ1行を付け、そのチャンクのヘッダに読み方の注意書きを入れる。

```
Jev事前スコア（0=問題なし寄り〜1=疑わしい）: 選択肢ヒント漏れ 0.9
```

Jev 未判定の問題・Jev 障害時は何も付かず、プロンプトは従来と完全に同一（変更前後のプロンプトを
突き合わせて確認済み）。

**設計上の懸念と対処**:

- **アンカリング**: 低スコアを「問題なし」と読んで確認を省くと、Jev が見逃す種類の欠陥
  （正解の誤り・解説のズレ）がそのまま素通りする。→ 注意書きで、Jev が見ているのはヒント漏れ
  だけで事実誤り・正解の当否・解説のズレ・ドメインは一切見ていないと明記し、確認観点は全問で
  通常どおり行うよう指示した。
- **高スコアだけで fix しない**: 正当な括弧（`（12シャード）` 等）でも高く出るため。
- **小数1桁に丸める**: スコアは同一入力でも最大0.1程度揺れるので、それ以上の桁は偽の精度。

**未検証**: このスコアを渡すと Claude の判定が良くなるのか、悪くなるのかは測っていない。
測るには Claude を実際に回す A/B が必要で、トークンを使う。

## 15. 本丸の問い — 静的解析で足りるのでは？

きっかけは「Jev の意味はある？ 静的解析では無理なこと？」という問い。

**反省**: 第9節の「正規表現との直接対決」は、括弧の有無を数えるだけの素朴な正規表現と比べていた。
Jev 側は質問を何度も作り直して探索・未見まで踏んだのに、静的側には同じ努力を払っていない。
藁人形との比較だった。**静的側にも同じ手順を踏ませて**比べ直した。

静的ルール（1行）: 「**数字を含まない括弧を持つ選択肢の割合**」。数量 `（12シャード）` や
参照記号 `（要件①）` は正当なので除く。ほかに、括弧率・略語展開／定義らしさ・
重みを学習させたロジスティック回帰（括弧6特徴）も比べた。

### 15.1 全体の AUC

| | 探索 | 未見 |
|---|---|---|
| Jev（選択肢のみ・1質問） | 0.803 | 0.836 |
| 静的: 数字なし括弧率 | 0.780 | 0.778 |
| 静的: 略語展開／定義らしさ | 0.745 | 0.788 |
| 静的: 括弧率 | 0.765 | 0.758 |

プールした差は Jev − 数字なし括弧率 = **+0.014〜+0.066**（P=0.999）。Jev が統計的に上だが、
差は約 +0.04 と小さい。重みを学習させた静的ルールが相手だと、未見で +0.030 [−0.004, +0.068]
（有意でない）。

### 15.2 括弧がある問題だけで比べる — 静的解析が苦手なはずの領域

括弧の有無では決まらない領域。ここで Jev が勝てなければ存在意義は薄い。
positive＝選択肢を修正された問題、negative＝Claude が ok と判定した問題（正当な括弧）。
探索は 63 / 39、未見は 63 / 30。

| | 探索 | 未見 |
|---|---|---|
| **Jev** | **0.785** | **0.749** |
| 静的: 数字なし括弧率 | 0.735 | 0.595 |
| 静的: 略語展開／定義らしさ | 0.689 | 0.666 |
| 静的: 括弧率 | 0.652 | 0.473 |

プールした差: Jev − 数字なし括弧率 = **+0.032〜+0.171**（P=0.998）、
Jev − 略語展開／定義らしさ = +0.010〜+0.171（P=0.986）。**ここは Jev の本物の優位。**
括弧率（有無だけ）は未見で 0.473、つまりランダム以下で、有無だけでは歯が立たない。

### 15.3 運用での効果 — 差がほぼ消える

1バッチ（プール90問から30問を選ぶ。有病率38%。ランダムなら11.4件）あたりの欠陥検出数。
帯幅は、同程度に疑わしい問題の中で古い順にするためにスコアを丸める幅。

| | 探索 帯0.25 | 探索 帯0.1 | 未見 帯0.25 | 未見 帯0.1 |
|---|---|---|---|---|
| Jev（採用構成） | 19.0 | 20.5 | 21.0 | 21.9 |
| 静的: 数字なし括弧率 | **20.2** | 20.5 | **20.2** | 20.2 |

- **帯0.25（日付優先を保つ現行設定）**: 平均で Jev 20.0、静的 20.2。**差なし**。
- 帯0.1 以下にすると Jev が平均 +0.8 件（約4%）上回る。
- Jev と静的の平均を取っても、Jev 単独より良くならない（未見 −0.016 [−0.037, +0.001]）。

Jev の優位（15.2）が帯0.25の運用の数字に出ないのは、粗い帯に丸めると上位の問題が同じ帯に
まとまり、Jev のスコアの分解能を捨ててしまうため。帯を0.01（ほぼ連続値）にすると
探索 20.7・未見 21.9 に戻ることから、そう読める。静的ルールは元々 0.25 刻み程度の粗い値しか
取らないので、丸めの影響を受けない。

### 15.4 結論

- **今回の用途（トリアージ）では、静的な1行ルールでほぼ同じ結果が出る。** 効果の大半は
  「怪しい順に並べる」という発想から来ていて、手段が Jev か静的かは二次的だった。
- **Jev が確かに優れていた点**: 括弧のある問題の中で「ヒント漏れ」と「正当な括弧」を、
  ルールを書かずに切り分けられること（AUC 0.75〜0.79 対 静的 0.60〜0.74）。最初の1質問で
  AUC 0.80 に届き、特徴設計も不要。費用は1問 $0.0003 と安く、確率と費用が構造化されて返る。
- **静的解析では無理なことを、Jev はできていない。** 意味的な欠陥（事実誤り 0.64・正解の当否
  0.47・解説のズレ 0.55）は Jev も判定できない。当初の構想「静的でできない確認を Jev に任せる」は
  成立しなかった。
- 残る判断: **A. 静的ルールに置き換える**（外部依存・費用・非決定性がなくなり、帯0.25なら同等）か、
  **B. Jev を残す**（帯を細かくすれば +4%、日付優先は弱まる）か。**未決定。**

### 15.5 限界

- 静的ルールの考案は探索データを見た後。ただし探索 0.780 → 未見 0.778 と再現しており、過学習ではなさそう。
- 欠陥検出数の差（約1件/バッチ）はブートストラップの誤差に近い大きさ。
- ラベルは Claude の判定で、13.2 のとおりノイズを含む。

## 教訓の追加（第8項の続き）

## 16. 使ってみた感触 — Jev はどこに向くか

依頼: 使ってみた感触として、静的解析でも LLM でもなく Jev が向きそうなのはどんなケースか。
記事に反映したい。

**整理の方法**: 次の3つを分けて書いた（`調査結果まとめ.md` §6c）。

- [実測] この用途で数字を取ったもの
- [実感] 使っていて感じたこと
- [推測] Jev の設計や今回の結果からの類推。試していない

**言えること**: Jev が確かに優れていたのは、ルールを書けない**浅い**判断（正当な括弧 対 ヒント漏れ）を
大量・安価に回し、確率として受け取れること。一方で深い推論・事実の検算・生成はできず、
ルールで書ける判断は静的解析で足りた。選び方は「静的で基準線 → 推論・生成が要れば LLM →
残りで静的を運用指標で超えるなら Jev」。

**言えないこと（最大の穴）**: **LLM との精度比較をしていない。** 今回比べたのは Jev と静的だけ。
「LLM ではなく Jev」の根拠は速度（約0.2秒/問 対 Claude の検証 約33〜62秒/問）と費用の桁の違いだが、
Claude の検証は検出＋修正まで含む別の仕事で、同じ条件の比較ではない。
測るなら、同じ hint_leak を Haiku などに採点させて AUC・時間・トークンを比べる。
サブスクのトークンを使うため、依頼があるまで実施していない。

**推測に留まるもの**: 毎ターン判定（公式の本来用途）、振り分け・トピック分類・簡易モデレーション・
RAG の関連度評価。いずれも Jev の3タイプに素直に乗る問いだが、自分では試していない。

**今回の用途が Jev に最適でなかった理由**: 欠陥の大半が機械的で、静的でも捉えやすかった
（第1節の決定的ルールで、構造的な不整合は全件0件・論点は選択肢の括弧にほぼ絞られていた）。
曖昧さが判断の中心にある用途なら優位が出るかもしれないが、これも推測。
